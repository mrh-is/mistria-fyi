## 1. Worktree Isolation

Every agent must operate inside an isolated Git worktree. Shared working trees cause edit
collisions, dirty-state confusion, & branch-switch destruction.

- Create worktrees under `.worktrees/<issue-number>-<short-description>`.
- Verify `.worktrees/` is ignored before creating: `git check-ignore -q .worktrees/placeholder`.
- Use the `superpowers:using-git-worktrees` skill.
- After `git worktree add`, recreate each entry listed in `.worktreeinclude` from the main checkout.
- Do **not** copy dependencies, caches, build artifacts, or writable generated directories.
- Run `pnpm install --frozen-lockfile` inside the new worktree.
- Run `pnpm run prepare` after installation to install Husky git hooks explicitly. (Lifecycle
  scripts may be disabled or skipped in some environments; this step ensures deterministic hook
  installation regardless.)

`.worktreeinclude` currently covers:

- `pipeline/input/` — shared read-only game assets. Symlink from the main checkout.
- `.env` / `.env.*` — machine-local configuration. Symlink or copy from the main checkout.

## 2. Git Configuration

The repo remote uses HTTPS (not SSH) and authenticates via `gh auth`. Commit signing uses a local
SSH key with `gpg.ssh.program = ssh-keygen`. Both are configured to work non-interactively so agents
can push and sign commits without triggering 1Password or other interactive prompts. Do not switch
the remote back to SSH.

## 3. Task Lifecycle

Follow this sequence for every task:

1. **Read the issue & comments** — use `gh issue view <number> --json title,body,labels,comments`.
   The `--comments` flag produces empty output when there are no comments; `--json` is reliable in
   all cases. Do not start issues labeled `blocked` or `discussion`.
2. **Invoke skills** — load the applicable Superpowers skills before exploration or implementation.
3. **Approval gates** — obtain explicit user approval at every specification and plan gate.
4. **Worktree** — create an isolated worktree before editing.
5. **Baseline** — install dependencies (`Node >=26`, `pnpm install --frozen-lockfile`) and verify a
   clean baseline.
6. **Understand contracts** — read the affected subsystem, its boundaries, and existing tests before
   editing.
7. **Test first** — add or update tests for behavioral changes, preferably before implementation.
   Run focused tests during development.
8. **Verification matrix** — run the complete verification matrix before committing. Lint must
   produce **zero errors and zero warnings**. If a warning requires an eslint-disable comment, add
   the narrowest possible disable with a justification comment.
9. **Commit specs & plans first** — commit approved specifications (`docs/superpowers/specs/`) and
   implementation plans (`docs/superpowers/plans/`) **before writing any implementation code**. If
   these files were created in the main checkout before the worktree existed, copy them into the
   worktree and commit them there as the first commit on the branch. This is not optional; specs and
   plans are deliverables that belong in the PR alongside the code they describe.
10. **Deliver** — commit, push, and open a PR that references the issue (`Closes #N`).

> Git pre-commit hooks are developer conveniences, not verification evidence. Agents must run the
> documented commands directly and verify clean exit status before committing.

## 4. Commands

Use **pnpm** exclusively. Do **not** use `npm`, `npx`, `yarn`, or `bun`.

| Command                       | Purpose                                    |
| ----------------------------- | ------------------------------------------ |
| `pnpm run dev`                | Dev server                                 |
| `pnpm run build`              | Production build (Cloudflare Pages)        |
| `pnpm run check`              | SvelteKit type checking                    |
| `pnpm run lint`               | Prettier + ESLint check                    |
| `pnpm run lint:fix`           | Auto-fix formatting & lint                 |
| `pnpm run test`               | Complete Vitest suite (asset-independent)  |
| `pnpm run test:app`           | App tests (`src/`)                         |
| `pnpm run test:pipeline`      | Pipeline tests (`pipeline/`)               |
| `pnpm run pipeline -- <path>` | Regenerate `tracker-data.json` from assets |

## 5. Architecture Boundaries

These rules prevent accidental damage to generated or vendored code:

- **`src/lib/data/tracker-data.json`** is generated by the pipeline. Never hand-edit.
- **`src/lib/types/tracker-data.ts`** is the shared data contract between pipeline & app.
- **`src/lib/engine/`** contains pure domain logic. Side effects belong at store or component
  boundaries.
- **`src/lib/stores/user-state.svelte.ts`** owns mutable progress & localStorage persistence.
- Save import merges progress additively. Backup restore replaces the serialized state. These flows
  are not interchangeable.
- Transfer encoding uses deterministic orderings derived from generated tracker data. Ordering &
  schema changes require compatibility tests & deliberate versioning.
- **`src/lib/components/ui/`** is vendored shadcn-svelte code. Do not manually edit.
- Category pages are layout compositors. Shared or stateful concerns belong in focused components.

## 6. Code Style

- **TypeScript**: `strictTypeChecked` ESLint + `strict: true` tsconfig. Use `type` imports
  (`consistent-type-imports`).
- **Formatting**: Prettier — double quotes, no tabs, trailing commas, 100 char width, semicolons.
- **Imports**: Auto-sorted by `perfectionist/sort-imports` — externals first, then `$lib`/`$app`
  internals, then relative.
- **Svelte**: Use `let` (not `const`) for `$props()` destructuring. Use runes (`$state`, `$derived`,
  `$effect`), not legacy stores.
- **Naming**: `camelCase` variables/functions, `PascalCase` types/components, `kebab-case` files.
  Branded IDs for type safety.
- **Rules**: `eqeqeq`, `prefer-const` (except `.svelte`), `no-var`, `object-shorthand`,
  `prefer-template`, `curly` (multi-line).

## 7. Token Efficiency

This project has a history of heavy agent usage. Follow these rules to keep token consumption
reasonable.

### Reading files

- **Use `offset` & `limit`** on the Read tool whenever you need a specific function, type, or
  section. Reading 30 targeted lines instead of 500 saves 10–20K tokens per call.
- **Never read `src/lib/data/tracker-data.json`** — it is large generated data. Read the types in
  `tracker-data.ts` or the pipeline source instead.
- **Don't re-read files you already have in context.** If compression has dropped a file's contents,
  re-read only the section you need, not the entire file.

### Verification & commands

- **Run the full verification matrix once before committing**, not after every edit. During
  development, run only the specific test file or check that covers your change.
- **Truncate verbose output.** Pipe lint, test, & build commands through `tail -30` unless you need
  the full output to diagnose a failure. Example: `pnpm run lint 2>&1 | tail -30`.
- **Batch grep patterns** into a single `rg` call with alternation rather than running separate
  searches.

### Session & agent strategy

- **Keep sessions focused.** One concern per session. Don't let sessions grow past ~100 turns if
  avoidable; long sessions pay a compounding context-compression tax.
- **Prefer forks over fresh subagents for research.** Forks share the parent's prompt cache; fresh
  agents pay the full context setup cost and re-read the same files from scratch.
- **Use subagent-driven development (SDD) sparingly.** SDD is expensive because each agent re-reads
  shared context files independently. Reserve it for genuinely parallelizable work with independent
  file sets. For most tasks in this project, sequential work with targeted forks is far cheaper.
- **Don't paste handoff reports when continuing across sessions.** Give the new session the branch
  name and issue number and let it read the PR/issue via `gh`. Handoff blobs duplicate what
  `gh issue view` and `git log` already provide.
