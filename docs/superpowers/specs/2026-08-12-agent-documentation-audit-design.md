# Agent documentation audit design

## Purpose

Make Harvest Helper safe and legible for agents with limited repository context. Every agent should
receive the universal operating rules from `AGENTS.md`, while task-specific details remain easy to
find without consuming every session’s context.

This pass covers documentation, workflow ergonomics, and small non-functional cleanup. Functional
defects and larger maintainability work discovered during the audit will become detailed GitHub
issues unless an existing issue already covers them.

## Documentation layers

`AGENTS.md` is the complete universal playbook. An agent should not need another document to learn
the mandatory workflow, repository boundaries, command policy, or minimum verification required for
ordinary work. It will stay concise enough to read every session and link to deeper documents when a
task enters a specialized subsystem.

Focused documents will carry details that apply only to particular work:

- `docs/development-workflow.md` will explain local setup, worktree mechanics, the Superpowers
  sequence, test-first implementation, the verification matrix, and common recovery steps.
- `docs/app-architecture.md` will explain generated data, runtime state, persistence, progress and
  availability semantics, route composition, save import, backup restore, and device transfer.
- `pipeline/README.md` will remain the canonical pipeline contract and troubleshooting guide.
- `docs/save-file-format.md` will remain the canonical binary save-format reference.
- Deployment and PWA documentation will be added only after the current service-worker activation
  path is verified. Unverified behavior will become a GitHub issue rather than a documentary claim.

`README.md` and `CONTRIBUTING.md` remain human-facing entry points. They will summarize setup and
contribution expectations, then link to canonical references instead of duplicating agent-only
instructions.

## Universal workflow

`AGENTS.md` will describe the full task lifecycle:

1. Read the GitHub issue and all comments. Do not start issues labeled `blocked` or `discussion`.
2. Invoke the applicable Superpowers skills before exploration or implementation. Get explicit user
   approval at every specification and plan gate.
3. Create an isolated worktree before editing.
4. Install locked dependencies with Node 26 and pnpm.
5. Establish a clean baseline before changing behavior.
6. Understand the affected subsystem and its contracts before editing.
7. Add or update tests for behavioral changes, preferably before implementation. Run focused tests
   during development.
8. Run the required repository-wide verification before committing.
9. Commit approved specifications and plans before their implementation begins.
10. Commit the completed work, push its branch, and open a PR that references the issue.

The instructions will explicitly state that Git hooks are a convenience, not proof of verification.
Agents remain responsible for running the documented commands themselves.

## Worktree-local files

`.worktreeinclude` identifies ignored local inputs that a worktree needs. Claude-managed worktrees
process this file automatically. Agents that create worktrees manually must recreate each existing
matched input in the new worktree after `git worktree add`.

For this repository, manual worktrees should use symbolic links for large or machine-local shared
inputs such as `pipeline/input` and `.env*`. This avoids copying the 114 MB game asset tree into
every worktree and keeps machine-local configuration consistent. Agents must treat linked pipeline
inputs as read-only.

Writable generated output must remain isolated. `pipeline/output` is derived, ignored, and created
by the pipeline, so it should not be shared between concurrent worktrees. This pass will remove it
from `.worktreeinclude`; each worktree will create its own output directory when the pipeline runs.

Before creating a project-local worktree, agents must verify that `.worktrees/` is ignored. They
must not link dependencies, caches, build artifacts, or other writable generated directories. Each
worktree runs `pnpm install --frozen-lockfile` independently.

## Architecture boundaries

The universal architecture map will identify the boundaries most likely to cause accidental damage:

- `src/lib/data/tracker-data.json` is generated by the pipeline and must never be hand-edited.
- `src/lib/types/tracker-data.ts` is the shared data contract between the pipeline and app.
- `src/lib/engine/` contains pure domain logic. Side effects belong at store or component
  boundaries.
- `src/lib/stores/user-state.svelte.ts` owns mutable progress and localStorage persistence.
- Save import and device transfer merge progress additively; backup restore replaces the serialized
  state. These flows are not interchangeable.
- Transfer encoding uses deterministic orderings derived from generated tracker data. Ordering and
  schema changes require compatibility tests and deliberate versioning.
- Progress scope and row visibility are separate. Hidden completed rows still count toward progress.
- `src/lib/components/ui/` is vendored shadcn-svelte code and is not manually edited.
- Category pages are layout compositors; shared or stateful concerns belong in focused components.

The app architecture document will expand these points, including localStorage keys, serialized and
ephemeral fields, tolerant save-import behavior, and the current availability model.

## Testing workflow

The repository will expose explicit pnpm scripts for the existing Vitest surface:

- `pnpm run test` runs the complete asset-independent suite.
- `pnpm run test:app` runs tests under `src/`.
- `pnpm run test:pipeline` runs tests under `pipeline/`.

The documentation will tell agents to add tests whenever behavior changes and to choose the
narrowest useful test during implementation. Before completion, every change runs:

```sh
pnpm run lint:fix
pnpm run check
pnpm run test
pnpm run build
```

Pipeline changes also run `pnpm run test:pipeline`. When local game assets are available and the
data contract or extractor output changes, agents also regenerate the pipeline output and review the
committed `src/lib/data/tracker-data.json` diff. Asset-dependent integration limitations will be
stated explicitly; fresh-clone portability is already part of the testing-infrastructure backlog.

Documentation-only changes still run formatting, linting, type-checking, tests, and link/path
checks. The production build remains part of final verification because SvelteKit and service-worker
errors can escape unit tests.

## Non-functional cleanup

This pass may make small changes that directly reduce agent error:

- add the explicit test scripts;
- remove `pipeline/output` from `.worktreeinclude`;
- replace committed `npx` or `bunx` usage with pnpm equivalents;
- correct stale category and route inventories;
- repair broken or misleading documentation links and commands.

It will not refactor application behavior or redesign pipeline contracts. Those findings belong in
separate issues with their own design and test work.

## Issue audit

Every deferred finding will be checked against open and recently closed issues before filing. A new
issue will include context, evidence with current file paths, impact, constraints, concrete
acceptance criteria, and verification expectations. Issues fixed in this PR will not be filed
separately.

The audit has already identified likely deferred work in these areas:

- recipe totals and `/all` rendering disagree about whether recipes are part of overall completion;
- the repository has no PR CI for linting, type-checking, tests, and builds;
- Husky installation is not deterministic in a fresh worktree;
- invalid backup restores fail without user feedback;
- PWA registration and offline behavior need explicit verification;
- pipeline requirement and source schemas lose information or express their contracts too loosely.

Existing issue #77 already covers general test scripts, transfer tests, `.sav` parser tests, broader
engine coverage, and generated-data invariants. New issues will link to it where related rather than
duplicating its scope.

## Delivery

The implementation will be reviewed for internal consistency and verified with the full command
matrix. The branch will contain the approved design and implementation plan as separate commits
before the documentation implementation commits. The final PR will summarize the documentation map,
workflow changes, non-functional cleanup, verification evidence, and every GitHub issue filed during
the audit.
